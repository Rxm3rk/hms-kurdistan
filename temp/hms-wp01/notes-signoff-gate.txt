"The sign-off gate cannot prove on its own that a human signed. The gate (`sh tools/hms safety check`, §3.5) accepts a sign-off record only if the working-tree record is the committed one and every commit in its history has a good signature (git `%G?` = `G`; `U` is rejected) by a key listed in `docs/safety/signoffs/allowed-signers.yaml` for the person and the role the record names. It trusts that list only as far as the list's own history allows, merges included: after a trust anchor, every change must be signed by a key that the trusted version before it lists, and a merge whose sides trust different versions, none of them the newest, by a key listed on every side (the fix of review findings R-01 and R-20). Until an external CI and a protected branch exist (DN-010), anyone with write access to this machine's repository, including an agent session, can add a key to the list in a trust-anchor commit. A trust anchor is the first commit that adds a key, a commit that adds a key after a listed signer has removed every key, or the first such commit in a rewritten history (a reset or a force-push) that leaves out the human's anchor. An anchor commit with an AI co-author trailer is rejected, but nothing stops one without a trailer. A commit made by an agent session with a listed signer's unlocked key also looks like the signer's own. The check reports every trust anchor as a warning. Until then, the automated reviewer and the human lead must verify every signer fingerprint in that file, and every trust anchor the check reports, out of band with the signer before trusting any record. Git verifies signatures with the host's own configuration, so each host that runs the gate of record needs the signers' GPG keys valid in its keyring, or their SSH keys in `gpg.ssh.allowedSignersFile` [HUMAN]. No signer is listed and no sign-off record exists yet."

RESIDUAL: 1. The KA-011 limitation remains, by design (plant 14). While the list holds no key, or after a listed signer removes every key, or in a rewritten history (reset or force-push) that leaves out the human's anchor, an agent commit without a trailer can be a trust anchor. The check only reports it as a warning. A listed signer's unlocked key used by an agent is also indistinguishable from the signer. Only out-of-band verification and DN-010 close this.
2. Departure from the verifier's suggested gap-4 fix ('an anchor version that does not validate should fail closed'). I judge each version by the schema committed with it. That makes the reported attack impossible: no later or uncommitted schema change can make a trusted version unreadable. A version that was already invalid when committed never conferred trust, so the next valid key-adding commit is a reported anchor, the same exposure as no anchor at all. Failing closed there would block the list for ever, because cited history is never rewritten (§3.6). This is documented in the README ('Who may sign') and in the GitAuthenticator docstring.
3. Departure from the verifier's 'probably' for the record log: it keeps git's default simplification (`git rev-list HEAD -- <record>`). Records carry no cumulative state, and the default history always follows the line that produced the content at HEAD, so the commit that wrote it is always checked. Real-git tests show a merge keeping an unsigned record version fails, and an unsigned merge bringing in a signed record passes. With --full-history, such legitimate unsigned merges would be listed and fail. This is documented in README step 3.
4. New fail-closed case, recorded as a Tightening [P]: a merge whose sides trust different versions and list no key in common can never be trusted. The README says to redo such a branch's change, signed, on the other line instead of merging.
5. Still open from before: the relaxation (an unsigned list change fails only until reverted or signed over), the other [P] tightenings, and host set-up [HUMAN] (each gate host must vouch for signers' keys).
