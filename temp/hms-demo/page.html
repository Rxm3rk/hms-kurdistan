WP-0.7Design system, patient banner and client shellsIn progressWindows laptop

The design system is the shared toolkit for how screens look and behave. Every screen of the hospital system is built from it, so buttons, numbers, dialogs and layouts work the same way in Sorani Kurdish, Arabic and English, with right-to-left layout for Kurdish and Arabic. Its centrepiece is the patient banner, the strip at the top of every clinical screen that always shows who the patient is: two identifiers (record number and date of birth), the name in Kurdish, Arabic and Latin script, the photo, allergies, code status, isolation and a dated weight. This matters because treating the wrong patient can kill. Around the banner it supplies one sign and co-sign pattern that checks the patient's identity again when someone signs soon after switching patients, a keyboard command palette, compact and comfortable density modes, and a device layer with a label-printer simulator, so every workstation handles printers, scanners and badge readers the same way.

8 of the 15 planned build slices are committed (the specification, core logic, the banner, sign and co-sign, the palette and the device client). The web frame and demo page exist only as uncommitted files, and there are no end-to-end tests, desktop shell or mobile app yet.

WP-0.8Documents and printing (wristbands, labels, receipts, PDFs)In progressWindows laptop

This is the part of the hospital system that prints wristbands, specimen labels, receipts, queue tokens and documents. Every patient print must carry two identifiers and the name in the patient's own script plus Latin. A name is never cut off, and the barcode must match the printed text, so staff do not treat or label the wrong patient. Kurdish and Arabic letters must join correctly or names print garbled, every print must say who printed it and be recorded, and patient data must never leave the hospital to be printed.

The specification is written and reviewed but only staged, not committed. Most of the print engine, the PDF renderer, the PDF/A checker and the printer test kit exist as uncommitted work that is being finished and reviewed piece by piece. The real templates, the print service and approved reference images have not been started, and nothing has been printed on a physical printer.

WP-0.5Clinical state machines and safety rulesIn progressWindows now → MacBook

Every clinical object in the hospital moves through a strict list of allowed steps: an order, a medication dose, a lab specimen, a result, a bed, a patient visit, an appointment and an insurance claim. Each step has named rules that must all be true before the step can happen. The software can only take steps that are written down, so it cannot skip a safety check such as scanning the patient's wristband: no step exists that leaves the check out. A tool turns these written rules into program code and into automatic tests that try about 1,000 random sequences of actions on each object, to show that no rule can be bypassed.

All eight machines, the generator and the generated code exist only as uncommitted files in the worktree; the newest auto-save is refs/wip/wp/0.5-state-machines at dc444ee, 11:07 on 19 Oct. The second review and the verification runs are still going, and nothing has been approved yet.

WP-0.3Core libraries: IDs, clocks, clinical time, money, doses and safe settingsIn progressWindows now → MacBook

These are the basic building blocks that every other part of the hospital system relies on. They give every record a number that can never clash with another, a clock that tests can control, two separate times on every clinical entry (when it happened and when it was typed in) so late charting always shows, money in Iraqi dinars and US dollars without rounding errors, and doses that cannot be entered without a unit. On top of these sit the settings rules, which let each hospital, ward and user adjust the system but never undo a safety setting the vendor has locked, and a task engine in which no piece of work can be left without an owner.

The nine specifications are written and have been through automated review. Code and tests for four of the six core libraries (identifiers, test clock, clinical and recorded time, money) are written, but nothing is committed and none of their tests has run yet: the builds are still queued on the overloaded build machine.

WP-0.2The on-site server cell, and its copy on the development laptopIn progressWindows laptop (Linux copy)

Each hospital will run a small cluster of three servers in its own building, called the "cell". It holds the database, messaging, sign-in and file storage, so the wards keep working when the internet link is down. This work package builds a copy of that cell on the development laptop. Every software image in it is pinned to an exact fingerprint, signed with a local key and served from a local registry. That lets the team prove the cell's safety promises, such as losing one server never losing a saved record, on the same design that hospitals will run.
