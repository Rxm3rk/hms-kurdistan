# Frontend workspace

The pnpm workspace for every HMS Kurdistan client (BUILD-PROMPT.md §5.4, §6.1, §6.5): the web workspaces,
the Tauri 2 desktop shell, the React Native mobile app, the queue signage and the packages they share.
WP-0.1 builds the workspace, its tooling and two packages (`eslint-plugin-hms` and `i18n`). The apps arrive
in WP-0.7.

## Layout

| Path                         | What lands there                                                                 | Built in                                                |
| ---------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------- |
| `apps/web`                   | React web workspaces, served from the cell                                       | WP-0.7                                                  |
| `apps/shell`                 | Tauri 2 desktop shell with the hardware abstraction layer                        | WP-0.7 (needs Rust)                                     |
| `apps/mobile`                | React Native app with Expo: nurse and physician modes                            | WP-0.7 skeleton; WP-3.3 (PLT-UX-04)                     |
| `apps/signage`               | Queue display boards (RTL HTML)                                                  | R1.1 (`ACC-OPD-01`), after WP-1.3                       |
| `packages/design-system`     | The one design system on React Aria Components, banner, `ClinicalNumber`         | WP-0.7                                                  |
| `packages/regulated-ui`      | Tier 2-owned display components with render-integrity checks                     | WP-1.5 first, then each Tier 2 module                   |
| `packages/api-client`        | TypeScript clients generated from the OpenAPI specifications                     | First needed in WP-0.7; regenerated by every API change |
| `packages/eslint-plugin-hms` | Lint rules `hms/no-jsx-literals`, `hms/no-physical-css` and the stylesheet check | WP-0.1                                                  |
| `packages/i18n`              | UI locales, ICU MessageFormat catalogues and the localisation lint               | WP-0.1; grows with every screen                         |

A directory without a `package.json` is a placeholder: pnpm does not treat it as a project.

## Commands

Run every command from `frontend/`. Corepack reads the pnpm pin from `frontend/package.json` in the current
directory only: run from the repository root, `corepack pnpm --dir frontend ...` falls back to the newest
pnpm, which then refuses to run a project pinned to another version (`ERR_PNPM_BAD_PM_VERSION`).

```sh
cd frontend
export COREPACK_ENABLE_DOWNLOAD_PROMPT=0
corepack pnpm install --frozen-lockfile
corepack pnpm run fast
```

`fast` is the frontend part of the fast tier (§19.1). It runs these in order and stops at the first failure:

| Script      | What it runs                                                                                 |
| ----------- | -------------------------------------------------------------------------------------------- |
| `lint`      | ESLint over the workspace (`lint:es`, warnings fail), then the stylesheet check (`lint:css`) |
| `typecheck` | `tsc --noEmit` for the root files and for every package                                      |
| `test`      | Vitest in every package; JUnit XML goes to `reports/junit/<package>.xml` (cleared first)     |
| `i18n:lint` | The localisation lint over `packages/i18n/src/messages`                                      |

`format` and `format:check` run Prettier. They are not part of `fast`.

The stylesheet check and the localisation lint can also be run directly, with `--json` for the programme
check contract (exit 0 pass, 1 fail, 2 usage error; last stdout line is one JSON object):

```sh
node packages/eslint-plugin-hms/src/css/cli.ts --json
node packages/i18n/src/lint/cli.ts --json
```

## Toolchain

Pinned by the version rule of BUILD-PROMPT.md §4.1 (the newest release line that has had a patch release,
supported by what depends on it). The direct versions are in the `catalog` of `pnpm-workspace.yaml`; packages
refer to them with `catalog:` and `pnpm-lock.yaml` pins the whole tree.

| Component         | Version | Note                                                                              |
| ----------------- | ------- | --------------------------------------------------------------------------------- |
| Node.js           | 24      | `engines.node` is `>=24 <25`; `engineStrict` enforces it                          |
| pnpm              | 12.12.1 | Through Corepack; `packageManager` carries the sha512 of the npm tarball          |
| TypeScript        | 6.0.3   | Not 7.x: typescript-eslint 8.71.2 supports TypeScript `>=4.8.4 <6.1.0`            |
| ESLint            | 10.9.1  | With `@eslint/js` 10.0.1                                                          |
| typescript-eslint | 8.71.2  | `strictTypeChecked` and `stylisticTypeChecked`, typed through the project service |
| Vitest            | 5.0.5   | On Vite 8.3.4                                                                     |
| Prettier          | 3.9.10  |                                                                                   |
| `@types/node`     | 24.13.6 | Types for Node.js 24.13 (the Windows checkout); the WSL build host runs v24.22.0  |

Install policy (`pnpm-workspace.yaml`): `saveExact`, `engineStrict` and `strictPeerDependencies`. pnpm 11 and
later read only registry and auth keys from `.npmrc`, which repeats the policy for npm-compatible tools and
points the private `@hms` scope at an unresolvable host so a workspace package can never be fetched from a
public registry by mistake. pnpm's default of running no dependency build scripts stands; no current
dependency needs one. `verifyDepsBeforeRun: error` makes every `pnpm run` fail with
`ERR_PNPM_VERIFY_DEPS_BEFORE_RUN` when `node_modules` does not match the lockfile, so install first on a fresh
clone; `updateNotifier: false` keeps pnpm from suggesting upgrades outside the version rule.

## Conventions

- Strict TypeScript and no `any` (§6.5). `tsconfig.base.json` holds the shared compiler options.
- Tooling runs as TypeScript directly through Node.js type stripping, so code uses erasable syntax only and
  relative imports carry their `.ts` extension.
- Every user-facing string comes from the ICU catalogues in `@hms/i18n`; `hms/no-jsx-literals` fails on
  literals in JSX. CSS uses logical properties only; `hms/no-physical-css` and the stylesheet check fail on
  physical directions (§6.5, §6.8 item 6).
- Text files are UTF-8 with LF line endings (`.gitattributes`, `.editorconfig` at the repository root).
