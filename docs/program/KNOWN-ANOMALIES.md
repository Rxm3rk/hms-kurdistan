| KA-011 | The sign-off gate cannot prove on its own that a human signed. The gate (`sh tools/hms safety check`, §3.5) accepts a sign-off record only if the working-tree record is the committed one and every commit in its history has a good signature (git `%G?` = `G`; `U` is rejected) by a key listed in `docs/safety/signoffs/allowed-signers.yaml` for the person and the role the record names. It trusts that list only as far as the list's own history allows, merges included: after a trust anchor, every change must be signed by a key that the trusted version before it lists (if that version does not validate, the last one before it that does); and where merged lines of history trust different signers, none of them the newest, no signer is trusted until every side has approved the signers of one version, a side either because it already trusts them or through a commit signed by a key it lists, so the keys of one side cannot make a signer trusted that another side does not already trust (the fix of review findings R-01 and R-20). Until an external CI and a protected branch exist (DN-010), anyone with write access to this machine's repository, including an agent session, can add a key to the list in a trust-anchor commit. A trust anchor is the first commit that adds a key, a commit that adds a key after a listed signer has removed every key, or the first such commit in a rewritten history (a reset or a force-push) that leaves out the human's anchor. An anchor commit with an AI co-author trailer is rejected, but nothing stops one without a trailer. A key anchored on a line that starts before the human's anchor (an agent's own, for example) does not become trusted when that line is merged unless a key of the human's line approves it, but the merge leaves no signer trusted until that line's keys approve a version too (or the other lines approve its own signers); if those keys are lost, the conflict can be settled only on that line's own signers, and only a rewrite of the history before any review cites the merge (§3.6) undoes the merge. A commit made by an agent session with a listed signer's unlocked key also looks like the signer's own. The check reports every trust anchor, and every commit that settles a conflict between merged lines, as a warning. Until then, the automated reviewer and the human lead must verify every signer fingerprint in that file, and every trust anchor the check reports, out of band with the signer before trusting any record. Git verifies signatures with the host's own configuration, so each host that runs the gate of record needs the signers' GPG keys valid in its keyring, or their SSH keys in `gpg.ssh.allowedSignersFile` [HUMAN].
