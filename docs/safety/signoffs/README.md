# Human sign-off records

A sign-off record is the only thing that allows an approval, sign-off, triage or risk-acceptance field to be filled anywhere in the safety artefacts or the state-machine specs (BUILD-PROMPT.md §3.5, §10.1). **Only a named person writes a record. The build agent never writes, edits or commits these files**, and never fills the fields they authorise; it asks for the decision in `docs/program/DECISIONS-NEEDED.md` with status `requested` and stops at the [HUMAN] gate. The build created `allowed-signers.yaml` in WP-0.1 with no entry, which is not a trust anchor; from then on the build agent never adds, changes or removes an entry in it and never commits a change to it.

`sh tools/hms safety check` fails when a filled field has no matching record, when a record is invalid, or when a record cannot be authenticated.

## The record

One YAML file per decision, in this directory, named `<id>.yaml`. The format is `signoff.schema.json`.

| Field | Required | Meaning |
|---|---|---|
| `id` | yes | `SO-<year>-<nnnn>`, for example `SO-2027-0001`; equal to the file name |
| `subject` | yes | The artefact the decision is about: a hazard id (`HAZ-0005`), a control id (`CTRL-0005-9`), a state-machine name (`medication-administration`, the spec's `machine` value), `risk-vocabulary`, or another artefact's id |
| `subject_version` | yes | The version of the subject that was decided on (see "Subject version"). The record authorises its field only while the subject is at this version |
| `field` | yes | The approval field it authorises, as a dotted path inside the subject: `residual_risk.accepted_by`, `cso_triage`, `approval.approved_by`, `approval` … A record for a parent path authorises the fields under it (`cso_triage` covers `cso_triage.by` and `cso_triage.date`) |
| `role` | yes | The role id in which the person signs, as `approval.required` writes it (Appendix B.3): `cso`, `pharmacist-panel`, `nurse-panel`, `lab-cso` … It must be a role `allowed-signers.yaml` lists for the signer, and one the field accepts (see "How the check matches a field to a record") |
| `name` | yes | The signer's full name, exactly as `allowed-signers.yaml` lists the holder of the signing key. The value written into a `…_by` field must equal this name (or the record id) |
| `date` | yes | Date of the decision, `YYYY-MM-DD`. A filled `cso_triage.date` must equal it |
| `statement` | yes | What exactly is approved, accepted or triaged, in the signer's words, with any conditions |
| `decision` | yes | `accepted`, `triaged`, `approved`, `rejected` or `returned`. Each of the first three authorises only its own kind of field: `accepted` authorises `residual_risk.accepted_by` (and with it a hazard `status: accepted`) and any other `accepted_by` key; `triaged` authorises `cso_triage` and any `triaged_by` key; `approved` authorises an approval block (`approval.approved_by`, `approval.record`, `approval.status`), a `risk_vocabulary.status` other than `proposed`, and any other `approved_by` or `signed_by` key. `rejected` and `returned` authorise nothing, and withdraw the records for the same subject version and field (see "Superseding and withdrawing") |
| `authentication` | yes | `{method: signed-git-commit}` in the MVP. An optional `signer_key` (the key's fingerprint) must then be the key that signed the record's commits |
| `evidence` | no | Paths or references to the evidence reviewed |
| `supersedes` | no | The id of an earlier record this one replaces; that record then authorises nothing (see "Superseding and withdrawing"). It must be another record that the check accepts, for the same subject and field (or a parent or a child of it); to end a rejection or a return, this record is by the same person or signs in the same role |
| `notes` | no | Free text |

Shape only (placeholders in angle brackets; this is not a record):

```yaml
id: SO-<yyyy>-<nnnn>
subject: <HAZ-nnnn | CTRL-nnnn-k | state-machine name | risk-vocabulary | artefact id>
subject_version: <the spec's version | sha256:<64 hex digits> as the check prints it>
field: <residual_risk.accepted_by | cso_triage | approval.approved_by | …>
role: <role id, for example cso>
name: <signer's full name, as in allowed-signers.yaml>
date: <yyyy-mm-dd>
statement: >-
  <what is approved, accepted or triaged, and any conditions>
decision: <accepted | triaged | approved | rejected | returned>
evidence:
  - <optional reference>
authentication:
  method: signed-git-commit
```

### Subject version

A record decides on one version of its subject; when the subject changes, the record stops authorising the field and the check fails until the person signs a new record (with `supersedes`) for the new version.

- A subject that carries its own `version` field (a state-machine spec, Appendix B.3) is at that version: `subject_version: 3` for `version: 3`. Whoever changes an approved spec raises its `version`; the check compares the numbers only, so it cannot see a change made without raising it.
- Any other subject (a hazard entry, a control, `risk-vocabulary`, an entry in a later safety artefact) has no version field, so its version is its content: `sha256:` and the SHA-256 of the subject's canonical JSON (sorted keys, no spaces, UTF-8) without the human fields. The human fields are every `approved_by`, `accepted_by`, `signed_by` and `triaged_by`, every `cso_triage` block, the `status`, `approved_by` and `record` of every `approval` block, and the subject's own `status` where that is an approval field (a hazard's, `risk-vocabulary`'s). An approval block's `required` roles are content: changing them changes the version. For a `triaged` record the content also leaves out the evidence of progress: each control's `state`, `implemented_in` and `verified_by`, and `residual_risk`. So building and verifying the triaged controls keeps the triage, while rewording, adding or removing a control, re-rating the initial risk or any other change voids it. An acceptance or an approval covers everything except the human fields, including the controls' states and their `verified_by` tests, and linked `releases` and `incidents`.

Filling the field itself (or the hazard's status) does not change the version. When a filled field has no matching record, or its record names another version, the check prints the subject's current version and the decision a record needs; the signer reviews the subject as it is now before copying that value into a new record.

### Superseding and withdrawing

A record never changes once committed, and is never removed, so a decision is taken back by a further record:

- A record withdraws the record its `supersedes` names, whatever either of them decides, if both are for the same `subject` and the same `field` (or a parent or a child of it); and a record that names a `rejected` or `returned` record ends that rejection or return only if it is by the same person (`name`) or signs in the same `role`, so one role or one panel cannot end another's rejection or return. The earlier record then authorises nothing any more, and it stays withdrawn even if its replacement is superseded in turn. `supersedes` must name another record that the check accepts and that it may supersede; otherwise it withdraws nothing, and the check fails until a later record supersedes the faulty one.
- A `rejected` or `returned` record withdraws every record for the same subject at the same `subject_version` whose `field` is its field, a parent or a child of it, whatever their role or date. A rejection or a return therefore stands until a record supersedes it, or until the subject changes (a new version needs new records anyway).
- A record committed at `HEAD` must be in the working tree: a record deleted there, or hidden by `assume-unchanged` or `skip-worktree`, fails the check. A record that a commit in `HEAD`'s history held but `HEAD` does not (deleted, renamed, or dropped by a merge) still withdraws what each version of it withdrew, if the rules below authenticate that version on the history up to the commit that held it; it authorises nothing, and the check reports it as a warning (not an error, because the commit that removed it stays in the record's history for good). So removing a rejection never brings back what it withdrew.

So a person who takes back an acceptance writes a `rejected` record (naming the acceptance in `supersedes`, or not), and a person who accepts after a rejection of the same version names the rejection in `supersedes`: the person who rejected, or another person in the same role (for a risk acceptance, a CSO). When a filled field rests only on withdrawn records, the check fails and names the record that withdrew each one. A record that the check does not accept (unsigned, or signed by a key the list does not hold) withdraws nothing, and the check fails on it.

## Who may sign: `allowed-signers.yaml`

`allowed-signers.yaml` is the human-maintained list of the keys whose holders may sign records, with the roles each person signs in (format: `allowed-signers.schema.json`). Each entry has the person's `name`, their `roles`, the `key_type` (`gpg` or `ssh`), the key's full `fingerprint` and the date it was `added`. A person with two keys has two entries. **The file ships with no entry: until a human adds one, no sign-off record can authorise anything, and the check says so on every run.**

The file has a history of its own, and the check trusts the committed version only as far as that history allows. It reads every commit that changed the file and every merge (`git rev-list --full-history --parents HEAD -- <file>`; git's default history simplification would hide a merge that keeps one side's version, and the line it did not follow). It reads each commit's signature and message on its own, so a message cannot pose as another commit, and it validates each version against the `allowed-signers.schema.json` committed with it, so no later change to the schema, committed or not, can make a trusted version unreadable. Then:

- A commit that adds a key where the trusted list holds none is a **trust anchor**: the first commit that adds a key, or one that adds a key after a listed signer has removed every key. It needs no signature but must not carry an AI co-author trailer, and nothing in the repository can show who made it. The check reports every trust anchor as a warning, and until an external CI and a protected branch exist (DN-010), the reviewer and the human verify each fingerprint in it with its holder out of band before trusting any record (`docs/program/KNOWN-ANOMALIES.md`, KA-011).
- Every other commit that changes the trusted version must have a good signature (`%G? = G`) by a key that the trusted version before it lists, whatever roles it lists the key for, and no AI co-author trailer. A commit that keeps or restores the trusted version needs nothing. A change that fails this is not trusted: the trusted version stays the one before it, and the check fails until the file is back at the trusted version (a revert) or a listed signer signs a new version. A version that does not validate trusts no one, but leaves the signers of the version before it in charge of the next change.
- For a merge, the trusted version before it is the newest side's: that of the side whose trusted version was set by a commit that descends from every other side's. A side on which the list has never held a key does not count, nor does a version that a trusted change on another side's line has since replaced. A merge that keeps the newest side's version needs nothing, so a branch that started before a signed change merges cleanly in either direction. A merge that keeps an older side's version is a change like any other, so a removed key does not come back without a listed signer's signature. Where no side is the newest (the list changed on both sides since they parted) but every side holds the same version, the merge is judged against that version; where the sides list the same signers in different texts, any merged text needs a signature by a key they list (or, if they list none, is a trust anchor when it adds a key).
- Otherwise the sides trust different signers and the list is **in conflict**: no signer is trusted until every side has approved the signers of one version. A side approves the signers it already trusts (those of its own version), and any other signers through a commit that sets the list to them with a good signature by a key that side lists and no AI co-author trailer; a side whose version lists no key (a listed signer removed every key) approves only a list without keys. The merge itself can approve, and so can any later commit that writes a version of the file, one that differs from the version in conflict: a signed comment-only edit is enough, because approvals count for the signers a version lists, not for its text. A commit that keeps the version in conflict, such as a routine merge of other work (`git rev-list --full-history` lists every merge), approves nothing, whoever signs it. A commit that changes the signers starts the approvals again, and a commit with an AI co-author trailer, or with a version that does not validate, approves nothing; a merge whose lines have already approved its signers on every side (a criss-cross merge) settles the conflict on those approvals, whatever it carries. So a key listed on every side settles a conflict in one commit, and the keys of one side cannot make a signer trusted that another side does not already trust: an agent that anchors its own key on a line that starts before the human's anchor, and merges that line, cannot take over the list. A human who signs a merged list that holds another side's key approves that key, as they would by signing it on one line, so the human reads what a merge of the list brings in before signing it. A revert of the merge is a change like any other and settles nothing. A later merge of a third line that changed the list on its own makes that line one more side: of the open conflict, whose approvals so far stand, or of a new conflict with the version that settled the first one. A version that settled the conflict on one line does not replace the sides of the same conflict on another line that holds a later approval of other signers with the key of a side whose approval the settlement rested on (the human signs the merged list, then signs a change back to their own key, while another line settles the merged list): those sides stay sides, of a new conflict with the settled version, so a key the human removed does not come back without the human's approval; and after any merge, an approval that a later approval with the same side's key has withdrawn does not count. Criss-cross and octopus merges follow the same rules, and approvals given on each line count. The error names the sides whose approval the committed version still lacks, and the check reports every settled conflict as a warning. A side approves other signers only with a key it lists. So a line on which the list was anchored on its own is never merged: if one is, the conflict lasts until a key of that line approves a version, and if every such key is lost, the conflict can be settled only on that line's own signers, whose keys are lost, and only a rewrite of the history before any review cites the merge (§3.6) removes it. If that line's own key removed every key on it, the conflict settles only on a list without keys, after which the next key is a new trust anchor, reported and verified out of band like the first (KA-011): the human then removes the merge by rewriting the history before any review cites it, rather than settle it and anchor again.
- Only the committed file counts; a working-tree file that differs from the committed one raises a warning and is ignored. In a shallow clone the history cannot be read, so no signer is trusted (an error once the file lists a key).
- The check reads the list, its schema and the records at their own paths: a symbolic link (or a junction) on the way in the working tree fails the check and leaves no signer trusted, and a link committed in their place is a change of that path like any other (a link to another list is not a trust anchor). Git runs without replace refs, grafts (`.git/info/grafts`) or the commit-graph file, so the history the check reads is the one the commits record, as in any other clone of the same commit.

Adding or changing an entry: a person the list already holds edits the file and commits it, signed with their listed key; the first entry, the trust anchor, is committed by the human lead without that signature. Removing a person's key withdraws every record that rests on it; keep the entry of someone who leaves unless their key is lost or compromised.

## How a record is authenticated (MVP)

The record counts only together with the signed git commit that adds it:

1. The named person writes the record and, in the same or a later commit, fills the field it authorises (for example `residual_risk.accepted_by: <name>` in `hazard-log.yaml`, or `approval.approved_by` and `approval.record: SO-…` in a state-machine spec).
2. They commit it with their own signing key (`git commit -S`, GPG or SSH signing), the key listed for them in `allowed-signers.yaml`. The commit carries no AI co-author trailer.
3. The check verifies, with git on the machine where it runs, that the record file is the committed one: `git status` shows no change, and its text equals the version at `HEAD`, so a change that `git update-index --assume-unchanged` or `--skip-worktree` hides from `git status` fails too. It verifies that **every** commit in the record's history (`git rev-list HEAD -- <record>`) has a good signature (`%G?` is `G`; `U`, a good signature by a key this host does not trust, is rejected) by a key in the trusted list (`%GF`, or `%GP`, the primary key, for a GPG subkey), whose entry has the record's `name` and lists the record's `role`, and that none carries an AI co-author trailer. That history follows, through merges, the line that produced the version at `HEAD`, so the commit that wrote it is always checked, together with every earlier version on that line; a version on another branch that a merge discarded is not part of it. Each commit is read on its own, so a message cannot pose as another commit. Every record committed at `HEAD` must be in the working tree, and a record that `HEAD`'s history held but `HEAD` does not is checked the same way on the history up to each commit that held a version of it, for what it withdraws (see "Superseding and withdrawing").

What is verified, and what is trusted:

- **Git verifies the signature** with the host's own configuration: for GPG, the signer's public key must be in the local keyring with full or ultimate validity (after `gpg --import`, certify it with the host's own key, `gpg --quick-lsign-key <fingerprint>`, or, on a host without a key of its own, set its owner trust, `echo '<fingerprint>:6:' | gpg --import-ownertrust`); for SSH, the key must be in the file that git's `gpg.ssh.allowedSignersFile` names. Otherwise git reports `U` or `N` and the record does not count. Each host that runs the gate of record (the WSL build host's clone; later the external CI) is set up this way by a human. The program git verifies with (`gpg.program`, `gpg.openpgp.program`, `gpg.ssh.program`, `gpg.x509.program`) must come from the host's global or system git configuration, or be the default: if the repository's own configuration (`.git/config`, a worktree's) or the command line sets one, the check trusts no signer (an error once the list holds a key), because that program is in no commit and could report a good signature by any key.
- **The check decides whom to trust**: only keys whose full fingerprint `allowed-signers.yaml` lists, as far as its history allows, for the names and roles listed there. A key that the host trusts but the list does not hold (for example one an agent generated in its own keyring) authenticates nothing.
- **What no check can tell**: who held the key when a commit was signed. A commit made by an agent session with a listed signer's unlocked key looks like the signer's own; the AI co-author trailer rule catches only a commit that declares its author. Signers keep their signing keys out of reach of agent sessions (a passphrase or a hardware key, no agent forwarding into the build host), and the trust anchor stays a matter for out-of-band verification (KA-011). Nor can the check see a history that `HEAD` no longer has: a rewritten history (a reset, or a force-push to a branch without protection) that leaves out the human's anchor makes a new trust anchor, which the check reports like any other. A local view of the same history (replace refs, `.git/info/grafts`, a commit-graph file) does not count: the check reads the commits as they are.

A committed record is never edited. A correction is a new record with `supersedes`. A record whose field is not filled yet raises a warning, not an error.

Stronger authentication (a qualified electronic signature, a signature-provider port, Q-K5) needs an ADR.

## How the check matches a field to a record

For every filled field it finds (the list is in `../README.md`, "Approval fields stay empty without a sign-off record"):

- the **subject** is the nearest enclosing object with an `id` (a hazard, a control, `risk-vocabulary`) or, in a state-machine spec, its `machine` name (else the file name);
- the **field** is the dotted path from that object (`residual_risk.accepted_by`, `cso_triage.by`, `approval.approved_by`);
- a record matches when its `subject` equals the subject, its `field` equals the path or a parent of it, its `decision` is the one the field needs (`accepted`, `triaged` or `approved`, as in the table above), its `subject_version` equals the subject's current version, no record has withdrawn it (see "Superseding and withdrawing"), and its `role` is one the field accepts. A hazard `status: accepted` needs a record for `residual_risk.accepted_by`; `approval.record` and `approval.status` are also authorised by a record for `approval.approved_by`, and a `risk_vocabulary.status` by a record for `approval` or `approval.approved_by`;
- the **role** the field accepts: `cso` for `residual_risk.accepted_by`, a hazard `status: accepted` and `cso_triage` (Appendix B.2, "[HUMAN] CSO only"); for an approval block, the roles its `approval.required` lists, and an approval block with no `required` roles cannot be authorised; for `risk-vocabulary` (its approval block and a `status` other than `proposed`), `cso` always, with any other role its `approval.required` lists, because changing the vocabulary or the matrix is a CSO decision. Any other `approved_by`, `accepted_by`, `signed_by` or `triaged_by` key names no role, so a record in any role listed for its signer can back it;
- an approval `status` other than `requested` needs a matching record for **every** role in `approval.required` (for `[pharmacist-panel, nurse-panel, cso]`, three records), while `approval.approved_by` may fill one approver at a time;
- the value must agree with the record: a `…_by` value equals the record's `name` or `id`, a date equals its `date`, and `approval.record` equals its `id`.

A record for a different subject, field, decision, version or role authorises nothing, and nor does a withdrawn one. An `approval` or `cso_triage` that is filled but is not a block (a text or a list, for example `approval: approved by the CSO`) can be backed by no record, so it always fails.

**Tightenings [P].** These rules go beyond §3.5 and the direction of review findings R-01 and R-20, and are this build's proposal: a record's `name` must be the name listed for its signing key; an approval `status` needs a record for every role in `approval.required`, and an approval block without `required` roles cannot be authorised; a trust anchor must not carry an AI co-author trailer; a merge whose sides trust different signers in `allowed-signers.yaml`, none of them the newest, leaves no signer trusted until every side has approved the signers of one version, and a side that lists no key approves only a list without keys; a shallow clone trusts no signer; a triage keeps its version while the controls progress, and any other change voids every record for the subject; a `rejected` or `returned` record withdraws the records for the same subject version and field until a record supersedes it, and only a record for the same subject and field by the same person or in the same role supersedes it; a record supersedes only a record for the same subject and field; a record committed at `HEAD` that is missing from the working tree fails, and a removed record's signed versions still withdraw; a commit that keeps the version of the list in conflict approves nothing; a settled version does not replace the sides of a conflict whose line has since withdrawn, with the same side's key, an approval the settlement rested on; a symbolic link on the path of the list, its schema or a record fails; the check ignores replace refs, grafts and the commit-graph file, and trusts no signer when the repository's own git configuration sets the program that verifies signatures; `risk-vocabulary` always needs the CSO, whatever its `approval.required` lists, and those roles are part of a subject's content version; an `approval` or `cso_triage` that is not a block always fails. One rule is a relaxation of the review's direction, for a reason: a change to `allowed-signers.yaml` that no listed key signed fails the check only until it is reverted or signed over, and a conflict between merged lines only until every side approves one version, not for ever, because a commit is never rewritten once a review cites it (§3.6), so a permanent failure could never be repaired.
