# Safety artefacts

This directory holds the safety evidence of HMS Kurdistan as data: the hazard log, its schema, the human sign-off records, and later the traceability matrix, the safety case, the Regulatory Boundary Register and the SOUP list (BUILD-PROMPT.md §3.1, §6.1, §10). CI reads it with:

```sh
sh tools/hms safety check          # human-readable
sh tools/hms safety check --json   # last stdout line is one JSON object {check, ok, counts, errors, warnings}
```

Exit code 0 means every rule passed, 1 means a rule failed, 2 means a usage or environment error (for example the plan of record or a Python dependency is missing).

Only a named human adds records or signers; the agent never does | WP-0.1 (format); no records yet, and no signer listed, so no record can authorise anything yet |

## The hazard log

Each entry follows the Appendix B.2 template and the §10.1 hazard record. The schema requires four fields that the B.2 example does not have. This is a deviation from the template, made on purpose and recorded here (§3.5):

| Required beyond the B.2 example | Why it is mandatory |
|---|---|
| `description` | §10.1 lists a description in the hazard record; the B.2 example omits it. It states the hazardous situation |
| `initial_risk.basis`, and `basis` in a proposed residual risk | This build's addition [P]. Every risk in the log is an agent proposal until the CSO triages it [HUMAN]; the basis says why it was proposed, so it cannot be read as an acceptance (§3.5) |
| controls: `risk_control_option` | §10.1 types every control as design, protective or information. In this log `type` holds this build's own vocabulary (Control types, below), so the §10.1 typing has a field of its own, required so that no control lacks it. Every seeded control carries it |
| controls: `planned_verification` (at least one test) | This build's addition [P]. §10.1 wants every control to carry the IDs of the tests that verify it; while a control is `planned`, `verified_by` stays empty, so `planned_verification` names those tests in advance and a reviewer can check the plan |

The B.2 example therefore does not validate as written: the check reports exactly these four missing fields, and with them added the example passes the whole check (`tools/hmstools/safety/tests/test_template_b2.py`). Relaxing the schema to the B.2 example plus optional extras was not chosen: it would let an entry omit the description that §10.1 asks for and a control omit its §10.1 typing, and it would make the two [P] additions optional. B.2 shows one entry only; the rest of the file (`schema_version`, `document`, `risk_vocabulary`, `seeded_hazards`) is this build's frame [P]. Every text field, these four included, must hold more than whitespace (`$defs/text` in the schema), so a mandatory field cannot be filled with blanks.

The seeded entries also use these fields. `seeded_hazard` is a B.2 field and required; the schema does not require the others except where noted:

| Field | Meaning |
|---|---|
| `seeded_hazard` | The seeded hazard the §2.1 table maps: one id (`H2`, as in B.2), a list where the table lists several (SI-12: `[H4, H2]`; SI-15: `[H2, H6]`), or `null` where it maps none (SI-18), with `seeded_hazard_note` saying why (required when `null`) |
| `related_seeded_hazards` | A proposal where `seeded_hazard` is null (SI-18): the harms that flow from the function, for CSO triage |
| `invariant_text` | The invariant quoted verbatim from the §2.1 table, so reviewers can check coverage. The check compares it with BUILD-PROMPT.md character for character, and requires one entry per SI that quotes it |
| `invariant_clauses` | The same text split into clauses with ids `a`, `b`, …; the clauses must rebuild `invariant_text` word for word (required together with `invariant_text`) |
| `enforced_in` | The §2.1 "Enforced in" column, quoted |
| `modules` | §5.2 modules that implement or depend on the invariant |
| `sac` | The §18.4 acceptance criteria the entry carries (every SAC that §18.4 maps to the SI must be listed) |
| `sensitivity_label` | For the SI-21 label entries: which label |
| controls: `covers` | Which clauses of `invariant_clauses` the control covers, or `preamble` for the §2.1 rules that hold for every SI (domain enforcement for every channel, vendor lock in the configuration chain, property-based tests and a nightly scenario suite) |
| controls: `sources` | Where the control comes from: `§n` is BUILD-PROMPT.md, `K §n` BLUEPRINT-KURDISTAN.md, `BP §n` BLUEPRINT.md, `SAC-nn` §18.4 |
| controls: `notes` | Free text. A tightening that the control proposes is recorded here (Tightenings, below), and so is a gap that the control leaves open for the CSO (open questions, below) |
| `incidents`, `releases` | Links to incidents and releases (§10.1); empty until used |

**Coverage rule.** Every clause of every invariant is covered by at least one control, and every SI entry has at least one control for the §2.1 preamble. The seeded controls are derived from the SI text, its "Enforced in" column, the §10.3 fallback control sets where they apply, the §18.4 SAC criteria and the module sections they cite. An invariant is never weakened, narrowed or reinterpreted; where a control proposes a mechanism the plan does not spell out, the control records it in `notes` as a tightening [P] and it is listed under "Tightenings" below, or it is an open question below. Where the plan's own control set for a clause leaves part of it without the protection the clause names (CTRL-0005-7: SI-05 clause d before the Dose Engine), the control says so in its description and `notes`, the part is not counted as covered, and it is an open question below.

### Control types

`type` is this build's vocabulary [P]: the plan defines no list of control types. The B.2 example shows `type: design`, and §10.1 types every control as design, protective or information, which this log carries in `risk_control_option`; `design` is valid in both. The values of `type`: `design` (a behaviour of the system), `test` (a check that blocks the build or a release), `process` (a human or organisational procedure, including RG obligations), `labelling` (what prints or screens show) and `training` (drills and training). The seeded mapping to `risk_control_option` is design → design; test → protective (a protective measure in the manufacturing process); alarms, hard stops and quarantines → protective; labelling, process and training → information for safety. The vocabulary and the mapping are [P], awaiting CSO confirmation.

### Test names

`planned_verification` and `verified_by` name tests as `<Kind>:<name>`, for example `PropertyTest:SI-02-override-reason-never-defaulted`, `ScenarioSuite:closed-loop-medication`, `AcceptanceTest:SAC-21`, `StaticAnalysis:no-dose-arithmetic-outside-reg-dose`, `ArchTest:…`, `GoldenImage:…`, `ChaosTest:…`, `EgressTest:…`, `CanaryScan:…`, `BoundaryTest:…`, `ContractTest:…`, `E2E:…`. A trailing `*` names a family (`PropertyTest:SI-01-*`). Tests carry these IDs in their names or tags (§18.1), so CI results can be keyed by them. `ScenarioSuite:` names follow §18.5; suites marked "(proposed)" are not named in §18.5 and are open below.

## Status lifecycle

| Hazard status | Who sets it | Needs |
|---|---|---|
| `open` | agent | — |
| `controls-implemented` | agent, with evidence | every control at least `implemented` |
| `controls-verified` | agent, with evidence | every control `verified` |
| `accepted` | **[HUMAN] only** | every control `verified`, `residual_risk.proposed` filled, `residual_risk.accepted_by` filled from a CSO sign-off record (`signoffs/`) |

| Control state | Needs |
|---|---|
| `planned` | — (every seeded control starts here) |
| `implemented` | `implemented_in` lists the code that implements it |
| `verified` | `implemented_in` and `verified_by` both non-empty; `verified_by` lists tests that **passed** in a recorded CI run (evidence under `docs/program/evidence/`) |

Never change a state to make a gate pass (§10.1). The check enforces the non-empty lists today; cross-checking that every `verified_by` test passed in the evidence run belongs to the CI promotion gate built in WP-0.9. A planned control that already lists `implemented_in` or `verified_by` raises a warning.

## Approval fields stay empty without a sign-off record

The agent never writes a person, panel or role into an approval, sign-off, triage or risk-acceptance field (§3.5). It leaves the field empty and asks for the decision in `docs/program/DECISIONS-NEEDED.md` with status `requested`. The check fails if any of these is filled without a matching, authenticated record under `signoffs/` (same subject and same field, the decision that field needs, the subject's current version, and a role the field accepts):

- `residual_risk.accepted_by`, and a hazard `status: accepted`;
- `cso_triage.by` and `cso_triage.date`;
- `approval.approved_by`, `approval.record` and an `approval.status` other than `requested`, in the state-machine specs under `docs/specs/state-machines/` (subdirectories included) and anywhere else;
- an `approval` or `cso_triage` that is filled but is not a block (a text or a list): no record can authorise it, so it always fails;
- `risk_vocabulary.status` other than `proposed`;
- any key named `approved_by`, `accepted_by`, `signed_by` or `triaged_by`, anywhere in the hazard log, in any YAML file under `docs/safety/` and in the state-machine specs.

A record that a later record supersedes, or that a `rejected` or `returned` record for the same subject version and field withdraws, authorises nothing (`signoffs/README.md`, "Superseding and withdrawing").

The subject of a field is the nearest enclosing object with an `id` (a hazard, a control, `risk-vocabulary`) or, in a state-machine spec, its `machine` name; the field is the dotted path from that object. How records are written, versioned and matched is in `signoffs/README.md`.

A record is authenticated only by git: the working-tree record must be the committed one, and every commit in its history must have a good signature (`%G? = G`) by a key listed in `signoffs/allowed-signers.yaml` for the person and role the record names. The list itself counts only as far as its own history allows, merges included: every change after its trust anchor must be signed by a key that the trusted version before it lists, and where merged lines of history trust different signers, none of them the newest, no signer is trusted until every side has approved the signers of one version, a side either because it already trusts them or through a commit signed by a key it lists (`signoffs/README.md`, "Who may sign"). **Limitation (KA-011):** the check cannot prove on its own that a human signed. While the list is empty, anyone who can commit here, an agent session included, can add a key in a trust-anchor commit; so can anyone who rewrites the history to leave out the human's anchor (a reset, or a force-push to a branch without protection); and a commit made with a listed signer's unlocked key looks like the signer's own. The check reports every trust anchor and every settled conflict; until an external CI and a protected branch exist (DN-010), the reviewer and the human verify each listed fingerprint with its holder out of band before trusting any record.

## Risk vocabulary [P] (awaiting CSO confirmation)

The vocabulary below is an engineering proposal of this build, marked [P] and binding only until the CSO confirms or changes it [HUMAN]. It follows the Appendix B.2 family. Severity is the worst credible harm to a patient; likelihood is judged for the hazard before the entry's controls (initial risk) or after them (residual risk). Until local incident data exists, likelihood is qualitative.

| Severity | Meaning |
|---|---|
| `negligible` | Inconvenience or temporary discomfort; no clinical effect |
| `minor` | Temporary harm that needs no professional medical intervention |
| `serious` | Harm that needs professional medical intervention |
| `major` | Permanent impairment or life-threatening harm |
| `catastrophic` | Death of one or more patients |

| Likelihood | Meaning |
|---|---|
| `improbable` | Not expected over the life of the product across all sites |
| `remote` | Could occur a few times over the life of the product across all sites |
| `occasional` | Could occur at a site from time to time (about yearly) |
| `probable` | Expected several times a year at a site |
| `frequent` | Expected often (monthly or more) at a site |

Risk level (`risk_vocabulary.matrix` in `hazard-log.yaml`; the check rejects a risk whose level disagrees with it):

| Severity \ likelihood | improbable | remote | occasional | probable | frequent |
|---|---|---|---|---|---|
| negligible | low | low | low | low | medium |
| minor | low | low | medium | medium | high |
| serious | low | medium | medium | high | high |
| major | medium | medium | high | very-high | very-high |
| catastrophic | medium | high | very-high | very-high | very-high |

Every seeded `initial_risk` is an agent proposal with a basis note, for CSO triage; it is never an acceptance. `residual_risk.proposed` stays null until the controls are verified.

## Open questions for CSO triage [HUMAN]

These came up while seeding; none is resolved by the agent.

1. **The risk vocabulary and matrix above**, the control `type` vocabulary and its mapping to the §10.1 options, and the tightenings listed above.

Until it is answered, CTRL-0014-4 and CTRL-0014-5 plan the stricter interim reading (Tightenings, above).
4. **Scenario suites §18.5 does not name** (§18.1 says every SI has a nightly scenario suite). §18.5 names no suite for SI-06, SI-07, SI-19, SI-20 and SI-21. For SI-09 and SI-18 it names a suite that exercises one part of the invariant, and the log cites it: #10 (seam: medication list as reconciliation input only) for SI-09, and #8 (deterioration: PEWS and MEOWS only where the Register allows) for SI-18. A dedicated suite is proposed for each of the seven: `record-immutability`, `ai-draft`, `medication-reconciliation`, `boundary-register`, `kill-switch`, `egress` and `sensitivity-labels`.
5. **Owners where the "Enforced in" column names no single §5.2 module:** SI-06 "Clinical journal" → `record-squad` (signed notes belong to `record`; the journal mechanics to `platform-journal`); SI-12 "RCM ↔ ADT/MAR boundary" → `rcm-squad` (it owns the §9.20 cross-boundary property test); SI-15 "Offline matrix; command handler" → `platform-site-squad`; SI-16 "Design-system shell" → `record-squad` (the banner is `CLN-CHT-01`; the design system is a frontend package with no §5.2 module).
6. **Seeded hazards without an entry yet:** H7 unavailability, H9 alarm not delivered, H11 cutover double dose and H15 cross-system seam failure are not mapped by any SI; their entries come with the work packages that build those areas.
7. **SACs without a hazard entry yet:** §18.1 says every SAC has a hazard ID. The 22 SACs whose §18.4 row names no SI (all except SAC-03, which HAZ-0001 carries) need entries; `tools/hms safety check` lists them as a warning.
8. **Initial risks** are proposals with no local incident data behind the likelihoods.
9. **SI-05 clause d before the Dose Engine** ("Hard stop at 10×/100× deviation."). Until `reg-dose` is active at a site, the only automated stop for such a deviation is the KB ≥10× Tier A rule (§10.3 A.2; CTRL-0005-10). It compares a KB-returned ratio, flag or maximum in the ordered unit with a governed threshold (§2.1 (c)), so it does not stop a 10× or 100× error that leaves the dose below 10× the KB maximum, a tenfold or hundredfold underdose, or an order for which the KB returns none of these ("dose check unavailable", pharmacist review). These errors are left to pharmacists: the independent double check (CTRL-0005-9) on every weight- or BSA-based dose, high-alert infusion and neonatal order; otherwise verification that asks for no independent calculation (§9.10); and, for a dose given under an override, the review within 4 h after it (CTRL-0005-12). §9.10 acceptance 2 and §10.3 A.3 expect seeded 10× errors to be stopped. The CSO decides whether this remaining gap of control set A is acceptable until the Dose Engine is active, whether the seeded errors must include such cases, and whether control set A needs a further control within the comparisons §2.1 allows. CTRL-0005-7 and CTRL-0005-16 record the gap, and the log does not count these errors as covered. The question is OQ-120 in `docs/program/OPEN-QUESTIONS.md`; it blocks nothing now and must be answered before R2b go-live at the latest.
